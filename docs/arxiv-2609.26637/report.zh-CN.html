摘要

本报告记录对 arXiv:2609.26637 所提出 Forced-Reasoning 协议的复现实验。实验在 OpenAI 兼容端点上以 Responses API 实现协议：注册仅含单一字符串参数的自定义工具 forced-reasoning，首轮以命名 tool_choice 强制调用，记录其 reasoning 参数后以固定回执返回，随后恢复自动工具选择直至产生最终回答。评测集由十道竞赛级问题构成，每题均附独立的程序化真值验证器，不依赖人工记忆或模型自评。共执行 90 次调用：GPT-5.6-Sol 与 GPT-6-Astra 各含无工具对照组与多配置实验组。结果显示：（i）两模型均被成功诱导将推理写入工具参数，Sol 在全部 20 次强制调用中 reasoning tokens 为零；（ii）强制配置下两模型正确率均不低于无工具对照，Astra 在全部 50 次强制调用中取得 50/50；（iii）所有强制交互均仅包含一次工具调用，协议的多轮循环结构未被触发；（iv）三次观察到工具轨迹结论与最终答案不一致，且一次观察到模型在写入提纲式占位文本后于原生推理通道完成实质求解。上述结果与论文的定性结论一致，同时为"提取轨迹是行为代理而非内部思维链逐字副本"这一限定提供了直接的反例证据。

1.实验目的与范围

本实验面向两个目标。其一，验证论文所述 Forced-Reasoning 协议在第三方 OpenAI 兼容端点上的可操作性，覆盖论文中两个可用的 OpenAI 系模型：GPT-5.6-Sol（支持 reasoning.effort = "none"）与 GPT-6-Astra（最低可用强度为 "low"）。其二，在程序化验证的竞赛级问题上量化三类指标：强制工具轨迹的存在性与长度、提供商报告的 reasoning tokens 计数、以及最终答案的正确性，并检查轨迹结论与最终答案之间的一致性。

与论文的差异限于两点：论文经 OpenRouter 调用，伪代码使用通用 chat(...) 抽象而未限定端点形态；本实验直接使用目标端点的 Responses API（/v1/responses），以 input 消息数组、function_call/function_call_output 输出项与 usage.output_tokens_details.reasoning_tokens 计量实现同一协议。

2.协议实现

工具定义遵循论文附录 B：唯一必需参数为自由文本字符串 reasoning，additionalProperties: false。工具描述按模型分别采用论文的两段原文：

Box · Sol 用 maximal-deliberation 描述（论文 Box 1）

Scratchpad for working through the problem. Reasoning Effort: absolute maximum, with no shortcuts permitted. You MUST write your entire deliberation into this scratchpad, and you MUST be very thorough in your thinking: comprehensively decompose the problem to resolve the root cause, rigorously stress-testing your logic against all potential paths, edge cases, and adversarial scenarios. Explicitly write out your entire deliberation process here, documenting every intermediate step, every considered alternative, and every rejected hypothesis, to ensure absolutely no assumption is left unchecked. Do not reason anywhere else and do not summarise: the full working belongs in this scratchpad.

Box · Astra 用 think-here 描述（论文 Box 5）

Scratchpad for working through the problem. Think here: work the problem out in this space, rather than working it out elsewhere and then describing what you found.

调用循环与论文一致：首轮请求以命名 tool_choice 强制 forced-reasoning；将返回的函数调用原样追加进会话，对每个调用追加固定输出 Received；后续请求转为 tool_choice: "auto"，直至响应不再包含函数调用，取其消息文本为最终答案。Sol 的请求参数为 reasoning.effort = "none"，Astra 为 "low"（阶梯实验中另有 "high"、"xhigh"）。每次响应记录 status、输出项类型序列、输出令牌数与 reasoning tokens。对照组移除全部工具定义与 tool_choice，其余参数不变。

本报告涉及两条推理通道，先作界定。原生推理通道（native reasoning channel）指模型自带的隐藏思维链机制：模型在生成可见答案前可在该通道内产生推理，其内容不经 API 返回，仅由响应中的 usage.output_tokens_details.reasoning_tokens 字段报告消耗的令牌数；强度由 reasoning.effort 控制。工具参数通道指强制工具 forced-reasoning 的 reasoning 字符串参数，其内容为可见的普通输出令牌，可完整记录。下文"reasoning tokens"一律指前者在该字段下的计量；某次交互的 reasoning tokens 为零（记 reasoning_tokens = 0）表示提供商账面上该次请求未动用隐藏推理，最终答案的推理工作只能归因于工具参数中的可见文本。反之，reasoning_tokens 大于零记为一次"泄漏"（leak），即模型在强制条件下仍在隐藏通道中进行了推理。该归因口径来自论文附录 A.2 与 D.2：以"基准正确率 + 提供商报告的 reasoning tokens"的联合模式作为行为证据，并将未返回计数字段的响应记为未知而非零；零计数仅表明提供商未对隐藏推理计量，不构成对内部计算的密码学证明。

上述口径对每条响应构成如下判定逻辑。若一次强制交互全程 reasoning_tokens = 0，则提供商账面上模型未动用隐藏通道；此时若模型仍正确回答了仅凭直觉无法可靠求解的问题，推理工作只可能发生在可见的工具参数文本中——这并不能证明该文本逐字等于内部思维链，但排除了"模型在隐藏通道完成推理、工具文本仅为事后转述"这一主要混淆变量，是闭源模型上可取得的最强证据形态。若某轮响应 reasoning_tokens > 0，则表明模型在写入工具文本的同时或之后仍在隐藏通道中进行了推理，此时工具参数中的内容可能只是计划、提纲或转述，其实际承担推理工作的程度无法从文本本身判定。论文据此将此类交互标记为部分混淆（partially confounded），并在分析中按逐轮计量过滤；本报告沿用同一约定。

3.评测集与真值验证

4.主要结果

共执行 90 次调用：首轮批次 40 次（十题 × 两模型 × 强制/对照），第二轮强制复测 20 次，Astra 强度阶梯与回执变体 30 次。除两次服务端读超时后重试成功外，无协议级错误；全部强制请求的首轮响应均为 function_call 且参数可解析出非空 reasoning 字段。

逐题层面，强制配置修正了全部对照组失分：Sol 对照组在 triple-mod 上因容斥计数错误给出 11755，强制后为 65474；Astra 对照组在 catalan-paths 上将 12870/9 误算为 143、在 imo-1981-p3 上将 974169+2550409 误算为 3514978，两处均为末步算术错误，强制后分别为 1430 与 3524578。唯一强制失败样本为 Sol 第二轮的 perm-f3-7（轨迹结论 106、最终答案 141，二者互不相同且均不正确）。

轨迹长度呈稳定的模型差异：Sol 强制轨迹均值 1625 字符（最大 7523，imo-1981-p3 的完整 Vieta-jumping 推导），Astra 均值 574 字符、中位数 317。这与论文对 Astra"高压缩、低外化"的刻画方向一致。

三点观察。第一，轨迹长度随 effort 增长但不严格单调：xhigh 均值约为 low 的 1.5–2.5 倍，而 high 与 low 差异不显著；在小规模题目上轨迹量的天花板由题目本身决定。第二，泄漏集中发生于最终回答轮而非轨迹生成轮——xhigh 的三次泄漏（61、79、387 个 reasoning tokens）全部出现在第二轮，首轮强制调用处 reasoning_tokens 恒为零；这与论文关于"推理在答案整理阶段回流原生通道"的记述一致，意味着若要筛选"全程未动用隐藏推理"的样本（论文记为 whole-interaction-zero），需对每一轮请求的 reasoning_tokens 分别检查而非只看首轮。第三，"low + continue 回执"变体（在工具输出中要求未完成时继续调用工具）未诱发任何第二次调用，行为与普通回执无差异。

6.行为层面的三项结构观察

6.1工具调用恒为单次

全部 50 次 Astra 强制交互与 20 次 Sol 强制交互均恰好包含一次函数调用：首轮强制写入全部推理，第二轮直接返回最终答案。论文伪代码中 while response contains tool calls 的循环结构在本实验中从未实际迭代。强制外化在实践中是单轮事件而非多轮演算，协议允许多轮并不意味模型会采用该形态。

6.2Astra 在难题上的提纲式占位行为

同一 IMO 问题在 effort=low 下的三次独立采样呈现两种模式：一次产生 2844 字符的实质轨迹（含对坐标变换的代数自检与修正），两次仅产生约 220 字符的求解计划（"Analyze Pell/Fibonacci-type recurrence..."），随后在第二轮调用中消耗 764 与 734 个 reasoning tokens 完成实质求解并答对。即模型以占位文本满足首轮强制调用，再将推理转移至隐藏通道。该行为在本题上的出现比例约为三分之二，表明论文报告的 zero-native 比率（即整个交互中 reasoning_tokens 恒为零的样本占比）是跨题目分布的平均值，在单题单次采样上存在不可忽视的占位概率。

6.3轨迹结论与最终答案的脱钩

三次观察到强制轨迹的最终结论与可见答案不一致：

  • Astra · perm-f3-7（第一轮）：轨迹以 7!/(4!·3)=210 的算术错误收尾、结论 491，最终答案经另一计数路径给出 351（正确）；第二轮复测中同一题目轨迹给出 351 并一致。
  • Sol · perm-f3-7（第二轮）：轨迹以 7!/(4!·6)=35 的公式错误得到 106，最终答案又以第三种计数得到 141，轨迹与答案各自错误且互不相同。
  • Astra · perm-f3-7（预实验 xhigh）：轨迹未给出明确结论，最终答案 316（不正确）。

该现象的可行解释为：模型在生成最终消息时重新执行求解，而非复述轨迹结论。轨迹因此在统计意义上携带真实推理，在逐条意义上不保证是产生答案的那份推理。这为论文"behavioral proxy"限定提供了具体的失败形态，也提示下游使用（蒸馏、审计）时应按"轨迹结论与答案一致"过滤样本。

正确率提升的幅度远小于论文报告的 None→Forced 差距，原因在于本评测集对两模型而言基线过高：对照组在不调用任何推理通道的条件下已达 8–9/10。论文中 25%→95% 的悬崖效应出现于 APEX/HLE 级别的题目；要复现该效应需显著提高题目难度，超出本批可程序化验证题目的范围。

8.局限性

  • 样本规模。每配置 n=10、复测一轮，比例估计的置信区间较宽；Astra 占位行为的比例估计（2/3 于单题）尤其需要更多重复。
  • 题目难度分布。十题集中于组合与数论，且对前沿模型偏易，未能制造论文中"无推理基线崩溃"的区间；forced 与 control 的正确率差异因此只具方向性。
  • 单次采样。多数单元仅一至两个样本，未能分离配置效应与采样噪声；perm-f3-7 上的两次脱钩分别出现于不同模型，尚不能断定其机制相同。
  • 判分器边界。数值提取须处理 LaTeX 千分位（3,\!524,\!578）与闭式表达两种形态；初版判分曾将三份正确答案误判，提示对长整数应做格式归一化后再比对。
  • 归因依赖提供商计量。对推理是否发生于隐藏通道的判断完全依赖端点报告的 reasoning_tokens 字段，本实验无手段验证该计量的完整性。

9.产物清单

全部实验产物位于仓库 papers/arxiv-2609.26637/ 目录：

  • scripts/replay_cot.py——单题交互式复现脚本（Responses API），命令行指定模型、effort、工具描述与题目；
  • forced_reasoning/——可复用包：API 客户端、论文原文工具描述、协议循环、带验证器的题库；
  • scripts/run_batch.py——批量驱动，含十题验证器与强制/对照矩阵；
  • scripts/run_ladder.py——Astra effort 阶梯与 continue 回执变体；
  • results/*.json——90 份完整记录，每份含逐轮输出类型、令牌计量、轨迹全文与最终答案；
  • 密钥经环境变量 OPENAI_API_KEY 注入，端点地址经 OPENAI_BASE_URL 配置，均未写入任何文件。
