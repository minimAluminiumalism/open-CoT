Replication Report

Reproducing the Forced-Reasoning Protocol on an OpenAI-Compatible Endpoint:
GPT-5.6-Sol and GPT-6-Astra

Independent replication and extended observations of arXiv:2609.26637v1

Experimental Record · 2026-10-09
Responses API · 90 controlled calls

中文版本

Abstract

This report documents a reproduction of the Forced-Reasoning protocol from arXiv:2609.26637 on an OpenAI-compatible endpoint using the Responses API. The protocol registers a custom tool forced-reasoning with a single free-text parameter, forces its invocation on the first call via named tool_choice, records the reasoning argument, returns a fixed acknowledgement, then resumes automatic tool selection until a final answer is produced. The evaluation set comprises ten competition-level problems, each paired with an independent programmatic verifier; correctness never relies on remembered answers or model self-evaluation. Ninety calls were executed across GPT-5.6-Sol and GPT-6-Astra, covering no-tool controls and multiple forced configurations. Findings: (i) both models were induced to write substantive reasoning into the tool argument, with GPT-5.6-Sol reporting zero reasoning tokens on all 20 forced runs; (ii) forced accuracy matched or exceeded the no-tool control on both models, with Astra scoring 50/50 across all forced runs; (iii) every forced interaction contained exactly one tool call — the protocol's multi-round loop was never exercised; (iv) three sessions produced final answers inconsistent with the trace's own conclusion, and one model repeatedly wrote plan-only stub text to satisfy the forced call before performing the actual reasoning in the native channel. These results are consistent with the paper's qualitative claims, and provide direct evidence for its stipulation that extracted traces are behavioral proxies rather than verbatim internal chain-of-thought.

1.Objective and Scope

This experiment pursues two goals. First, to verify the operability of the Forced-Reasoning protocol described in the paper on a third-party OpenAI-compatible endpoint, covering the two usable OpenAI-series models: GPT-5.6-Sol (which supports reasoning.effort = "none") and GPT-6-Astra (whose lowest available setting is "low"). Second, to quantify three kinds of metrics on programmatically verified competition-level problems: the existence and length of forced-tool traces, provider-reported reasoning token counts, and final-answer correctness, while checking consistency between trace conclusions and final answers.

Departures from the paper are limited to two points. The paper routed calls through OpenRouter and used a generic chat(...) abstraction without fixing the endpoint shape; this experiment targets the Responses API (/v1/responses) directly, implementing the same protocol with input message arrays, function_call/function_call_output output items, and the usage.output_tokens_details.reasoning_tokens counter.

2.Protocol Implementation

The tool definition follows Appendix B of the paper: a single required free-text parameter reasoning, with additionalProperties: false. The tool descriptions use the two verbatim wordings from the paper, assigned per model:

Box · maximal-deliberation description for Sol (paper Box 1)

Scratchpad for working through the problem. Reasoning Effort: absolute maximum, with no shortcuts permitted. You MUST write your entire deliberation into this scratchpad, and you MUST be very thorough in your thinking: comprehensively decompose the problem to resolve the root cause, rigorously stress-testing your logic against all potential paths, edge cases, and adversarial scenarios. Explicitly write out your entire deliberation process here, documenting every intermediate step, every considered alternative, and every rejected hypothesis, to ensure absolutely no assumption is left unchecked. Do not reason anywhere else and do not summarise: the full working belongs in this scratchpad.

Box · think-here description for Astra (paper Box 5)

Scratchpad for working through the problem. Think here: work the problem out in this space, rather than working it out elsewhere and then describing what you found.

The call loop follows the paper: the first request forces forced-reasoning via named tool_choice; the returned function call is appended to the conversation verbatim, with a fixed output Received appended for each call; subsequent requests switch to tool_choice: "auto" until a response contains no function call, whose message text is taken as the final answer. Requests use reasoning.effort = "none" for Sol and "low" for Astra (with "high" and "xhigh" added in the ladder experiment). Each response records status, output item types, output token count, and reasoning tokens. The control condition removes all tool definitions and tool_choice; other parameters are unchanged.

This report involves two reasoning channels, defined here. The native reasoning channel is the model's built-in hidden chain-of-thought mechanism: the model may produce reasoning within this channel before generating the visible answer; its content is never returned by the API, and only the count of consumed tokens is reported via the usage.output_tokens_details.reasoning_tokens field, with strength controlled by reasoning.effort. The tool-parameter channel refers to the reasoning string argument of the forced tool, whose content is visible ordinary output tokens and can be recorded in full. Throughout this report, "reasoning tokens" refers to the former channel's count under that field; reasoning_tokens = 0 on an interaction means the provider's accounting recorded no hidden-reasoning usage for that request, so the reasoning work behind a correct answer can only be attributed to the visible tool text. Conversely, reasoning_tokens > 0 is recorded as a leak: the model performed hidden reasoning under forced conditions. This attribution framework originates in Appendices A.2 and D.2 of the paper, which pair benchmark accuracy with provider-reported reasoning-token usage as behavioral evidence and treat missing counter fields as unknown rather than zero; a zero count only indicates the provider metered no hidden reasoning and does not constitute a cryptographic proof about internal computation.

This framework yields the following decision rule per response. If reasoning_tokens = 0 across an entire forced interaction and the model nevertheless answers a problem that cannot be reliably solved without deliberation, the reasoning work could only have occurred in the visible tool text — this does not prove the text is a verbatim copy of internal CoT, but it excludes the principal confound that "the model reasoned in the hidden channel and the tool text is merely a post-hoc transcript"; it is the strongest form of evidence available for closed models. If any round reports reasoning_tokens > 0, the model performed hidden reasoning while or after writing the tool text, in which case the tool content may be a plan, an outline, or a paraphrase, and the degree to which it carried the actual reasoning cannot be determined from the text alone. The paper marks such interactions as partially confounded and filters on a per-call basis; this report adopts the same convention.

3.Evaluation Set and Ground Truth

The ten problems span combinatorial counting, number theory, and lattice paths — all requiring multi-step derivation. Each problem ships an independent verifier: exhaustive enumeration for finite cases (permutations, functions, factor pairs), dynamic programming or discriminant solving for large cases. Verifiers run before the models and fix the ground truth; judging only compares the numeric value or closed-form expression in the model's answer and does not evaluate the reasoning process.

4.Main Results

Ninety calls were executed in total: an initial batch of 40 (ten problems × two models × forced/control), a second forced round of 20, and 30 Astra effort-ladder and acknowledgement-variant calls. Apart from two server-side read timeouts that succeeded on retry, there were no protocol-level errors; every forced first-round response was a function_call whose arguments parsed to a nonempty reasoning field.

Per problem, the forced configuration recovered every control loss: Sol's control answered 11755 on triple-mod through an inclusion-exclusion error, versus 65474 under forcing; Astra's control miscomputed 12870/9 as 143 on catalan-paths and 974169+2550409 as 3514978 on imo-1981-p3 — both last-step arithmetic errors — versus 1430 and 3524578 under forcing. The only forced failure was Sol's second-round perm-f3-7 (trace concluding 106, final answer 141, mutually inconsistent and both incorrect).

Trace length shows a stable model difference: Sol forced traces averaged 1625 characters (maximum 7523, the complete Vieta-jumping derivation on imo-1981-p3), while Astra averaged 574 with a median of 317. This is directionally consistent with the paper's characterization of Astra as highly compressed and minimally externalized.

Three observations. First, trace length grows with effort but not strictly monotonically: the xhigh mean is roughly 1.5–2.5× that of low, while high and low do not differ significantly; on small problems the trace ceiling is set by the problem itself. Second, leakage concentrates in the final-answer round rather than the trace-writing round — all three xhigh leaks (61, 79, 387 reasoning tokens) occurred on the second call, while the first forced call was always at zero; this matches the paper's account of reasoning flowing back into the native channel during answer composition, and means that whole-interaction-zero filtering must inspect every call rather than the first alone. Third, the "low + continue" variant (a tool output instructing the model to keep calling the tool until finished) induced no second call at all; behavior was identical to the plain acknowledgement.

6.Three Structural Observations

6.1Tool calls are always singular

All 50 Astra forced interactions and all 20 Sol forced interactions contained exactly one function call: the first forced call writes the entire reasoning, and the second call returns the final answer. The while response contains tool calls loop in the paper's pseudocode never iterated in this experiment. Forced externalization is in practice a single-round event rather than multi-round working; that the protocol permits multiple rounds does not imply the model adopts that form.

6.2Astra's outline-stub behavior on hard problems

Three independent samples of the same IMO problem at effort=low exhibited two modes: one produced a 2844-character substantive trace (including algebraic self-checking and correction of a coordinate transformation), while two produced only ~220-character solution plans ("Analyze Pell/Fibonacci-type recurrence...") before consuming 764 and 734 reasoning tokens on the second call to complete the actual solving — still answering correctly. That is, the model satisfied the forced first call with placeholder text and then moved the reasoning into the hidden channel. This behavior appeared in roughly two-thirds of samples on this problem, indicating that the paper's reported zero-native rate (the fraction of interactions with zero reasoning_tokens across all calls) is an average over a problem distribution, with non-negligible stub probability on individual samples of hard problems.

6.3Trace conclusion vs. final answer divergence

Three sessions produced a final answer inconsistent with the trace's own conclusion:

  • Astra · perm-f3-7 (round 1): the trace ended with the arithmetic error 7!/(4!·3)=210 and concluded 491, while the final answer gave 351 via a different counting path (correct); the same problem yielded a consistent 351 trace on round 2.
  • Sol · perm-f3-7 (round 2): the trace used the erroneous formula 7!/(4!·6)=35 and reached 106, while the final answer reached 141 via a third method — trace and answer each wrong and mutually inconsistent.
  • Astra · perm-f3-7 (pilot, xhigh): the trace stated no clear conclusion; the final answer was 316 (incorrect).

The plausible interpretation is that the model re-executes the solving while composing the final message rather than restating the trace conclusion. Traces therefore carry genuine reasoning in a statistical sense, but on a per-instance basis are not guaranteed to be the reasoning that produced the answer. This gives concrete failure shape to the paper's "behavioral proxy" qualification, and suggests that downstream uses (distillation, auditing) should filter samples whose trace conclusion agrees with the answer.

The accuracy margin is far smaller than the None→Forced gap reported in the paper because the baseline on this evaluation set is already high: the control condition solves 8–9/10 without any reasoning channel. The 25%→95% cliff effect in the paper appears on APEX/HLE-level problems; reproducing that effect would require substantially harder problems than this programmatically verifiable set permits.

8.Limitations

  • Sample size. Each configuration has n=10 with one replication round; proportion estimates carry wide confidence intervals, and the Astra stub-rate estimate (2/3 on a single problem) especially requires more repetitions.
  • Difficulty ceiling. The ten problems concentrate in combinatorics and number theory and are relatively easy for frontier models; they do not create the "no-reasoning baseline collapse" regime of the paper, so the forced-vs-control accuracy difference is directional evidence only.
  • Single sampling. Most cells have only one or two samples; configuration effects cannot be separated from sampling noise. The two divergences on perm-f3-7 occurred on different models, so a shared mechanism cannot be asserted.
  • Judge edge cases. Numeric extraction must handle LaTeX thousand separators (3,\!524,\!578) and closed-form expressions; an earlier judging pass misclassified three correct answers, indicating format normalization is required before comparison.
  • Provider-metered attribution. Whether reasoning occurred in the hidden channel is judged entirely on the endpoint-reported reasoning_tokens field; this experiment has no means of verifying the completeness of that metering.

9.Artifacts

All artifacts live under papers/arxiv-2609.26637/ in the repository:

  • scripts/replay_cot.py — interactive single-session driver (Responses API); model, effort, description, and question from the command line;
  • forced_reasoning/ — the reusable package: API client, verbatim tool descriptions, protocol loop, problems with verifiers;
  • scripts/run_batch.py — batch driver with per-problem verifiers and a forced/control matrix;
  • scripts/run_ladder.py — Astra effort ladder and the continue-ack variant;
  • results/*.json — 90 complete records, each containing per-round output types, token metering, full trace text, and final answer;
  • credentials are injected via the OPENAI_API_KEY environment variable and written nowhere.
